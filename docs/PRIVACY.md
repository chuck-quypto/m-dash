# What m-dash stores and connects to

m-dash stores settings and usage history locally in `%LOCALAPPDATA%\net.chuckdudley.mdash\usage.sqlite` on Windows or `~/Library/Application Support/net.chuckdudley.mdash/usage.sqlite` on Mac. Records include account identifiers needed to keep accounts separate, observation times, plan names, allowance/credit measurements and numeric token totals. On Ubuntu development builds the directory is `${XDG_DATA_HOME:-$HOME/.local/share}/net.chuckdudley.mdash`. The directory also contains SQLite working files, WebView cache and, when configured, Claude feed helper/configuration files.

Claude local history also stores opaque session and request identifiers to associate and deduplicate events. For each model request reported by the optional feed it keeps accounting metadata: model, token counts by type (input, output, cache read, cache write), the provider's API-equivalent cost estimate, effort and speed settings, whether the request came from the main session, a subagent or compaction (with an opaque agent identifier), and where it ran (terminal, desktop, an SDK or a cloud session). It also records when a request was refused for a reached allowance. Per-window allowance readings and these limit events are kept for 400 days; per-request accounting rows are folded into daily totals by model, purpose and location after 90 days. They are metadata, not login credentials, but can link activity within the local history. Daily token totals and the latest reading for each account remain until you remove the data directory. To keep long-running installs small, m-dash removes raw allowance readings and idle Claude session records after 30 days, and folds Claude request identifiers older than 35 days into daily totals before removing them. Turning off a provider or feed preserves those records.

The app does not retain conversations, user-authored prompts, commands, raw provider-process output or subscription login tokens. Codex, Claude and Grok keep control of their own authentication. An explicitly connected OpenRouter management key is stored in Windows Credential Manager, macOS login Keychain or the Linux desktop Secret Service keyring; it is not sent to the web interface or saved in the usage database.

Enabled collectors ask the installed provider CLIs for account/usage information. OpenRouter collection sends authenticated HTTPS requests to OpenRouter's credit/activity API. These reads do not generate model completions. The optional Claude feed sends selected accounting metadata to an authenticated receiver on this computer's loopback interface. These collectors do not send data to an m-dash service. Optional mobile sync is separate and requires explicit pairing consent; its connections and retention are described below. m-dash has no analytics collector.

The Claude statusline helper selects accounting fields before sending. Claude's OTLP exporter sends its telemetry payload to the loopback receiver, where m-dash filters fields before storage. Do not assume the transport contains only the values retained in SQLite; its contents also depend on the installed CLI and telemetry settings. If the receiver cannot run, the feed is suspended and its managed settings are removed. Each receiver start retires the previous token; a replacement is published only after the receiver owns its socket. A healthy enabled feed stays enabled with its new endpoint. Incomplete cleanup blocks recovery. Already-running Claude processes retain their exporter environment and must be restarted to use the new endpoint; m-dash cannot retract telemetry they already sent. See the [recovery instructions](USER_GUIDE.md#choose-your-accounts).

The receiver listens on fixed loopback port 43183 and authenticates requests with a per-start token. It assumes a single-user computer: on a shared machine, another account that binds that port first could receive the feed's token and accounting metadata. Leave the local feed off on shared computers.

Claude ping is an optional action, separate from collection and off by default. After you confirm its usage notice, m-dash can send the fixed prompt `ping` through your existing Claude subscription CLI using Haiku 5.5 at low effort. This consumes allowance and may consume paid credits if extra usage is enabled with Claude. The request is made by Claude Code to Anthropic; m-dash does not copy subscription tokens or use an API-key fallback. A unique empty working directory, safe mode and disabled tools reduce context; Claude Code's own authentication and managed policy still apply. Generated response text is discarded. The local database keeps account-bound consent, last observed window, attempt timestamp/outcome and CLI-reported token count when available. Ping metadata is separate from the optional local token feed, and is not added to that feed's totals.

Turning Claude ping off stops future automatic launches. A submitted request may finish. A changed sign-in requires new confirmation. Turning the Claude provider off also disables ping; turning only the local feed off leaves the separately selected ping setting unchanged. Codex automatic pings are unavailable pending testing.

Turning a provider off stops new reads and local-feed recording, hides its displayed data and preserves its history and credentials. A request already in flight may complete; its result is discarded. OpenRouter **Disconnect** removes the stored key and retains history. Claude **Disable local feed** removes only m-dash's additions to Claude settings.

Keep the data directory for upgrades or backups. Copy it after quitting m-dash so the database and its working files are consistent. If uninstalling, leave the application-data deletion option unchecked to retain history. A saved credential and Claude's external settings are separate from this directory; disconnect/disable their integrations in Settings before uninstalling if you want those removed too.

The Windows installer may download Microsoft's shared WebView2 runtime when missing; Microsoft manages that runtime and its updates separately. Mac uses Apple's system WebKit runtime. Ubuntu development builds use system GTK/WebKitGTK, libsecret and a native Zenity prompt; no secret enters process arguments or environment, and no plaintext credential fallback is used. Provider services and CLIs have their own privacy policies.

## Optional encrypted mobile sync (development)

Settings → Mobile companion on Windows or Mac can share enabled providers' allowance windows, USD balances and up to 30 days of numeric daily token history with paired Android phones. The export replaces account identifiers with opaque per-pair values. Provider credentials, prompts, responses, logs, collection and pings stay on the desktop. The phone cannot execute commands, trigger collection or send pings. iPhone remains pending.

Sync is off until you review the disclosure, create a private ten-minute pairing code, compare verification values and approve the phone on desktop. Keep the code private. Each phone has independent encryption and access keys. Windows Credential Manager or Mac Keychain holds the desktop keys, durable sequence state and relay enrollment access in dedicated entries separate from provider credentials. Android Keystore protects phone pairing and cached state in backup-excluded storage. The relay receives ciphertext and hashed access tokens, never the decryption keys or provider credentials.

No hosted relay is provided. The reference relay in `relay/` is designed for Cloudflare Workers and a D1 database you deploy yourself; the retention described here applies to that design. It keeps only the latest active encrypted snapshot per phone and expires it after seven days without a new desktop upload; reads do not extend expiry. Replaced/deleted ciphertext may remain recoverable in paid D1 Time Travel for up to 30 additional days. This is not proof of physical erasure. Cloudflare can observe IP addresses, connection timing and payload sizes. Application payload logging is disabled, which does not remove Cloudflare's infrastructure metadata.

The desktop uploads once per minute while running. Phone refresh only retrieves saved readings and retains their original observation times. Protected local copies can remain visible as stale after relay expiry. Revoke on desktop to stop future delivery; revocation waits for connectivity if the relay is unreachable. Disconnect and clear on Android to remove that phone's local copy. Revocation cannot erase copies already held by a phone. Uninstalling either app does not by itself revoke relay access. If you deploy a relay, its backups and logs are under your control and need your own retention review.
