# Development sync protocol: pairing v2, envelope v1

Experimental protocol, outside the desktop release scope. Test pairing/approval, authenticated envelope admission, allowlisted snapshot export, protected persistence and Android refresh/restart separately. This document does not promise a hosted service or release acceptance.

Desktop creates a per-phone random 256-bit AES key, independent random 256-bit bootstrap/write bearer tokens, and a random channel ID. The relay receives only token SHA-256 hashes. A ten-minute `mdash2:` pairing code carries the HTTPS relay origin, channel, bootstrap token, AES key and expiry directly to the phone; it must be transferred privately and is never uploaded. No provider secret, login, prompt, response or raw log is exported.

Phone generates a fresh random read token and claim nonce, saves both durably, then claims the pending channel using the bootstrap token and sends `{claim, readHash}`. The relay atomically binds the first nonce/read-hash combination; only identical retries succeed. Snapshot reads require the fresh phone token, which never appears in the code. The bootstrap token cannot read snapshots, including legacy channels without a phone read hash. Desktop and phone display a verification value derived from SHA-256(key || claim nonce); the owner compares it and approves on desktop. Approval is bound to that exact claim. Only a pairing approved before its ten-minute relay deadline can upload or read; approval remains valid until revocation. Client code parsing permits five minutes of clock skew, but the relay enforces its own deadline. Persist approval intent before sending it, and allow the same approved claim to retry after the deadline. New phones use separate keys/channels. Deleting a channel removes its snapshot and credentials on relay; the desktop retains a local revocation intent until remote deletion succeeds. Expired codes without approval intent are removed locally; an expired unapproved approval is queued for revocation. Snapshot expiry never deletes approved pairing authority.

AES-256-GCM uses an independently random 96-bit nonce per upload and authenticates protocol version, channel, sequence and publication time as associated data. Snapshot source is the channel ID, avoiding a cross-phone tracking identifier. Durable desktop sequence is incremented before sending; gaps are valid. Phone rejects wrong-source, modified, backwards or conflicting repeated snapshots and persists the high-water state before reporting success. Requests/responses are bounded, time-limited, HTTPS-only with redirects refused. No arbitrary browser network bridge is exposed.

Desktop secret state lives in macOS Keychain or Windows Credential Manager. Windows stores the bounded pairing set in one native credential so keys, approval/revocation intent and durable sequences are replaced together; a write exceeding the native 2560-byte limit fails before upload and preserves the saved credential. Android encrypts the complete pairing and cached snapshot state using an Android Keystore AES key, writes atomically, excludes backups and fails closed on storage/authentication errors. Browser previews cannot pair or store live data. A compromised unlocked desktop/phone remains outside E2EE's protection. A copied code can compete for the initial claim, so private transfer and matching verification remain necessary. After claim, a copied code alone cannot authorize relay reads. It still contains the AES key: it can decrypt ciphertext obtained through another compromise. This bootstrap scheme does not provide forward secrecy or protection against a compromised relay colluding with a holder of the code.

Snapshot schema v2 adds a bounded display label and nullable duration to every allowance window. Spending windows and Grok allowances without a known start remain visible without inventing a duration. Clients retain strict v1 admission for authenticated cached readings; new desktop exports use v2. Envelope version/AAD remain v1 and authenticate the entire snapshot. Invalid source values become unavailable rather than fabricated values. Each phone's validation/upload failure is isolated; durable-state write failures stop publication.

## Upgrade requirement

Do not update just one component of a live setup. Stop publishers and disable the Worker before upgrading. For an existing database created from the old schema, apply `relay/migrations/0002_phone_read_authority.sql` once; a fresh database uses `relay/schema.sql` instead, not both. Use a new relay epoch and new enrollment secrets, install the matching Worker and desktop/Android clients, then resume only after synthetic and private device checks. Old channels must not retain active read authority. Revoke/remove legacy entries on desktop and explicitly disconnect/re-pair phones with new codes. The updated desktop pauses legacy publication; Android keeps authenticated old cached readings available with a re-pair warning.

The relay has a separate operator enrollment secret for creating channels, an environment epoch outside D1 recovery, bounded active channels and request limits. Deployment logging must exclude payloads and Authorization headers. It stores only the latest ciphertext, expiring after seven days; reads do not renew it. Expiry clears ciphertext while preserving approved pairing authority and sequence so a returning desktop can resume. Authenticated local phone copies remain available as stale readings. Replaced/deleted ciphertext may remain in paid D1 Time Travel for 30 additional days. Endpoint IP/timing/size metadata is visible. No paid plan is activated automatically.

Recovery procedure: never restore D1 in place under an active Worker. Disable the relay, rotate its environment epoch and enrollment secret, restore into a new database, bind that database with the new epoch, then resume. Old-epoch records are rejected. All devices must re-pair. This operational gate prevents a database restore from restoring revoked authority; it is not automatic detection of an operator bypassing that procedure. Test restored old rows against a new epoch before enabling real data.

Before live-data acceptance: review crypto/protocol and connected callers; exercise wrong keys, tampering, expiry, approval, read/write separation, replay, revocation, recovery epoch, retained state and native protected cache. Then qualify a development deployment and your own device. Source tests/emulator evidence do not establish physical-device or public-release acceptance.
